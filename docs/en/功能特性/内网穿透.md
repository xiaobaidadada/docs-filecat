# Tunneling

Make services without a public IP reachable from the internet.

FileCat bundles FRP-based tunneling where **both ends are FileCat** — no separate frps deployment.

## Know which end is which

- **Server** — runs on the machine **with a public IP**, accepts external connections
- **Client** — runs on the **internal machine** you want to expose, reports its local services

Both machines run FileCat. Getting the direction backwards is the usual reason nothing connects.

## Step 1: configure the server (public machine)

1. Open **Settings → Tunneling → Server**
2. Set the **listening port**, e.g. `7000` (clients connect here)
3. Set an **authentication token** — any sufficiently long random string
4. Save and start the server
5. **Open the port in your cloud provider's security group and the local firewall**

> Always set a token. Without one, anyone can connect to your server and relay traffic through it.

## Step 2: configure the client (internal machine)

1. Open **Settings → Tunneling → Client**
2. Enter the **server address** (the public machine's IP or domain)
3. Enter the **server port** (the 7000 from the previous step)
4. Enter the **token** (must match the server exactly)
5. Save

## Step 3: add a forwarding rule

Tell the client what to expose:

| Field | What to enter | Example |
| --- | --- | --- |
| Local address | The internal service | `127.0.0.1:8080` |
| Remote port | The port for external access | `18080` |

After saving, `public-ip:18080` equals the internal `127.0.0.1:8080`.

> The remote port must also be opened in the public machine's firewall.

## Typical case: exposing a home service

1. Install FileCat on a cloud host, configure the server, open ports 7000 and your service ports
2. Install FileCat at home, configure the client to point at the cloud host
3. Add a rule: local `192.168.x.x:5000` (a NAS admin page) → remote `15000`
4. Visit `cloud-ip:15000` from outside to reach the NAS console

## Typical case: reaching internal devices

Router admin pages and internal Windows remote desktops tunnel out the same way.

For RDP, set the local address to `internal-ip:3389` and pick any remote port.

## P2P direct mode

In normal mode data passes through the server relay, limited by the server's bandwidth.

P2P mode tries to hole-punch a direct connection between both ends:

- Success: data bypasses the server — lower latency, higher bandwidth
- Failure: falls back to relay mode automatically

Success depends on both NAT types; symmetric NAT usually fails.

## Security advice

- **Always set a token** — this is the baseline
- Never expose databases, Redis or similar sensitive services to the internet
- Prefer exposing HTTPS services; avoid plaintext on the public internet
- Combine with FileCat's access control to restrict source IPs

## It connects but is unstable?

Check in this order:

1. **Firewall** — both the server port and the remote port must be open. Cloud security groups and the OS firewall are separate; both need changing
2. **Token mismatch** — if the client cannot reach the server, verify the token first
3. **Version mismatch** — keep client and server on the same FileCat version
4. **Bandwidth** — relay mode is limited by the server's outbound bandwidth; for heavy traffic consider P2P
